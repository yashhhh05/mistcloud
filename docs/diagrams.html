1. System context

Who talks to what, and which external services are optional.

flowchart TB
    U["User in a browser"]
    subgraph APP["Mist Cloud"]
        SPA["React SPA
routes, auth context, upload UI"]
        API["Express API
/api/auth, /api/files, /api/search"]
    end
    DB[("MongoDB
users + file metadata")]
    OBJ[("AWS S3 bucket
file bytes")]
    DISK[("backend/uploads
local fallback bytes")]
    SMTP["SMTP server
OTP email"]
    U -->|"HTML, JS, CSS"| SPA
    SPA -->|"JSON + JWT / multipart"| API
    API -->|"Mongoose"| DB
    API -->|"PutObject / DeleteObject"| OBJ
    API -->|"fs.writeFile / unlink"| DISK
    API -->|"sendMail (optional)"| SMTP
    API -->|"302 redirect to presigned GET"| U
    U -->|"GET file bytes directly"| OBJ
    U -->|"GET /uploads/:key"| API

In plain words

Picture a shop. The browser is the shop front, the Express API is the back room, and three storerooms sit behind it.

  • React app — what the user sees and clicks. Every click becomes a JSON request, or a file upload.
  • Express API — the only part allowed into the storerooms. It checks the token, decides what is allowed, then calls a service.
  • MongoDB — index cards: file name, size, category, owner, share list. No file content lives here.
  • S3 / backend/uploads — the actual bytes of the file.
  • SMTP — used for one thing only: emailing the login code. Without it the code is printed in the server log.

The interesting arrows are the download path. When S3 is active, opening a file returns a 302 redirect to a temporary signed link, so the browser fetches the bytes straight from S3 and the API never carries them. Local-disk mode has nowhere to redirect, so Express streams the file itself.

2. Runtime topology — two entry points

The root server serves API + built SPA on :3000. The standalone backend on :5000 exists for the Vite dev proxy.

flowchart LR
    subgraph A["Mode A — npm run dev / npm start (root)"]
        A1["Browser"] --> A2["server.js :3000"]
        A2 --> A3["/api → backend/routes"]
        A2 --> A4["/uploads → backend/uploads"]
        A2 --> A5["dist/ static + SPA fallback"]
        A3 --> A6[("MongoDB or in-memory")]
        A3 --> A7[("S3 or local disk")]
    end
    subgraph B["Mode B — Vite dev + standalone API"]
        B1["Browser"] --> B2["Vite dev server :3000
HMR"]
        B2 -->|"proxy /api and /uploads"| B3["backend/server.js :5000"]
        B3 --> B4[("MongoDB or in-memory")]
        B3 --> B5[("S3 or local disk")]
    end

In plain words

There are two ways to start this project, and they behave differently.

  • Mode A — one process. server.js on port 3000 is the whole app: it answers /api, serves /uploads, and serves the compiled frontend from dist/. This is what npm run dev and npm start do, and it is closest to deployment.
  • Mode B — two processes. Vite runs the frontend on 3000 with hot reload, and backend/server.js runs the API on 5000. Vite's proxy forwards /api and /uploads, so the browser still sees one origin.

The catch: root npm run dev builds first and then starts Mode A, so editing a React file does nothing until you rebuild. It is not the hot-reload loop people expect.

3. Server startup decision

What root server.js does depending on whether dist/ exists.

flowchart TD
    S["startServer()"] --> Q{"does dist/ exist?"}
    Q -- "no" --> V["import vite, createServer middlewareMode"]
    V --> V2["app.use(vite.middlewares)"]
    Q -- "yes" --> P["express.static(dist)"]
    P --> P2["static public/ + frontend/public/"]
    P2 --> P3["GET fallback (not /api, not /uploads) → dist/index.html"]
    V2 --> L["app.listen(3000, 0.0.0.0)"]
    P3 --> L

In plain words

This is the first decision the server makes at boot: is there a compiled frontend to serve?

  • dist/ exists — serve it as static files. Any URL that is not /api or /uploads returns dist/index.html. That is what makes client-side routing work: /images is not a real file, so the server hands back the app shell and React Router shows the images page.
  • dist/ does not exist — start Vite in middleware mode inside Express, which compiles .tsx on demand and adds hot reload.

Either way the process listens on 0.0.0.0:3000. Because npm run dev runs vite build first, the second branch is effectively dead in normal use.

4. Backend layers

Routers → middleware → controllers → models/services → data layer, with the fallback branches.

flowchart TB
    REQ["HTTP request"] --> MW0["cors, express.json / urlencoded"]
    MW0 --> R{"routes/index.js"}
    R -->|"/auth/*"| AR["auth.routes"]
    R -->|"/files/*"| FR["file.routes"]
    R -->|"/search"| SR["search.routes"]
    AR --> C1["auth.controller"]
    FR --> AM["authMiddleware (JWT)"]
    AM --> UM["multer.memoryStorage (upload only)"]
    UM --> C2["file.controller"]
    SR --> AM2["authMiddleware"]
    AM2 --> C3["search.controller"]
    C1 --> US["User model / in-memory users"]
    C1 --> MS["mail.service (nodemailer)"]
    C2 --> FS["File model / in-memory files"]
    C2 --> SS["s3.service (put, delete, presign)"]
    C3 --> FS
    C3 --> SS
    SS --> S3C["config/s3.js → S3Client or local disk"]
    FS --> DBC["config/db.js → Mongoose or memory"]

In plain words

A request walks down this stack like a visitor in an office building.

  1. Reception (cors, express.json) decides which sites may call and unpacks the body.
  2. Switchboard (routes) sends the request to the auth, file or search router.
  3. Security guard (authMiddleware) verifies the JWT and loads the user. No user, no entry.
  4. Mailroom (multer) exists only on upload: it catches the file and holds it in memory.
  5. Worker (the controller) does the real job: classify, save, list, rename, delete.
  6. Records and warehouse: metadata through a Mongoose model, bytes through s3.service.

Every controller then forks: Mongo or in-memory, S3 or local disk. That fork is why each feature has two code paths.

5. Frontend route tree

flowchart TD
    ROOT["/ BrowserRouter"] --> PUB["Public"]

    GUARD --> RL["RootLayout"]

    RL --> FV["/:type — FilesView

In plain words

The app has two zones.

  • Public pages — /sign-in and /sign-up.
  • Guarded pages — everything behind ProtectedRoute. It shows a spinner while checking the saved token, redirects to /sign-in if there is no session, otherwise renders the shared layout.
  • Anything else — an unknown URL sends you back to / instead of a 404.

Inside the guarded area there are only two screens: the dashboard and one category page reused four times (documents, images, media, others). The URL segment is translated into the types value the API expects; any other segment means “no filter”, so it shows every file.

In plain words

Read the tree top to bottom; each arrow means “renders”.

  • App wraps everything in AuthProvider, so any component can ask who is logged in.
  • ProtectedRoute is the door; RootLayout draws the persistent shell: sidebar, mobile drawer, header with search and upload, toasts.
  • The shell owns one small piece of state, refreshTrigger, and passes it plus handleRefresh to the current page through the router's outlet context.

So the shell owns when to refresh, pages own what to fetch, and cards own what can be done to one file.

7. Session bootstrap

Token from localStorage → /auth/me → user, or logout on 401.

sequenceDiagram
    autonumber
    participant B as Browser
    participant AC as AuthProvider
    participant AX as Axios interceptor
    participant API as Express API
    B->>AC: mount App
    AC->>AC: read token + user from localStorage
    alt no token
        AC->>AC: user = null, isLoading = false
    else token present
        AC->>AX: GET /api/auth/me
        AX->>AX: attach Bearer token
        AX->>API: request
        alt 200
            API-->>AC: user JSON
            AC->>AC: setUser + persist
        else 401
            AX->>AX: clear storage, dispatch auth-unauthorized
            AC->>AC: logout()
        end
    end
    AC-->>B: ProtectedRoute renders Outlet or redirects

In plain words

Refresh the page and the app has to remember who you are.

  1. It reads token and user from localStorage.
  2. No token → signed out immediately.
  3. Token present → it calls GET /api/auth/me to confirm the token is still valid and get fresh user data.
  4. 200 → the user is stored again and the guarded pages render, with no login screen.
  5. 401 → the interceptor deletes the token and user, the context logs out, and the guard sends you to /sign-in.

The same interceptor runs on every later request, so an expired token logs the user out on their next action rather than at a fixed time.

8. Refresh after a mutation

No cache, no optimistic updates: mutate → toast → increment refreshTrigger → re-fetch.

sequenceDiagram
    autonumber
    participant U as User
    participant AD as ActionDropdown / FileUploader
    participant API as Express API
    participant RL as RootLayout
    participant P as Dashboard / FilesView
    U->>AD: rename / share / delete / upload
    AD->>API: PATCH / DELETE / POST
    API-->>AD: result
    AD->>AD: toast
    AD->>RL: onRefresh → refreshTrigger + 1
    RL->>P: new context value
    P->>API: GET /files (+ /files/usage)
    API-->>P: fresh documents

In plain words

There is no cache and no optimistic update; the app simply asks again.

  1. The user renames, shares, deletes or uploads.
  2. The component calls the API and shows a toast.
  3. On success it bumps refreshTrigger in RootLayout.
  4. That value flows to the current page, whose effect depends on it.
  5. The page re-runs GET /files (and /files/usage) and re-renders.

Blunt but predictable: the screen always reflects what the server just returned, at the cost of one extra round trip per change.

9. Sign in, OTP, JWT

Password check, fixed OTP 123456, 30-day JWT stored in localStorage.

sequenceDiagram
    autonumber
    actor U as User
    participant SI as SignIn / SignUp
    participant API as auth.controller
    participant DB as MongoDB or memory
    participant MAIL as nodemailer
    participant LS as localStorage
    U->>SI: email + password (+ fullName)
    SI->>API: POST /auth/signup or /auth/signin
    API->>DB: find user by email
    API->>API: bcrypt.compare or accept "password123"
    API->>DB: otpCode = 123456, expiry = now + 10 min
    API->>MAIL: send OTP (failure ignored)
    API-->>SI: accountId
    SI->>U: open OTP modal
    U->>SI: 6-digit code
    SI->>API: POST /auth/verify
    API->>DB: find by accountId, else demo user
    API->>API: accept 123456 or stored code
    API->>API: jwt.sign userId, 30d
    API-->>SI: token + user
    SI->>LS: persist token + user
    SI->>U: navigate to /

In plain words

Login is a three-act play: password, code, badge.

  1. The form sends email + password (plus full name on signup).
  2. The server looks the user up; signup refuses an existing email, in-memory signin creates unknown users.
  3. It compares the password with bcrypt, which stores a scrambled hash, never the password itself.
  4. It stores a code with a 10-minute expiry and tries to email it; mail failure is ignored.
  5. Only accountId comes back, so the UI opens the code dialog.
  6. /auth/verify accepts 123456 or the stored code, then signs a 30-day JWT.
  7. The browser saves token + user in localStorage and navigates to the dashboard.

The password proves what you know, the code should prove you own the inbox, and the JWT is the wristband for 30 days. Here the code is always 123456 and its expiry is never checked, so the wristband is effectively free.

10. Upload

Bytes: browser → multer RAM → S3/disk. Metadata: controller → Mongo/memory.

sequenceDiagram
    autonumber
    actor U as User
    participant FU as FileUploader
    participant AX as apiClient
    participant MW as multer
    participant FC as file.controller
    participant ST as s3.service
    participant OBJ as S3 or disk
    participant DB as File model or memory
    U->>FU: drop file
    FU->>FU: reject > 50 MB
    FU->>AX: POST /files/upload FormData
    AX->>MW: multipart + Bearer
    MW->>FC: req.file buffer
    FC->>FC: getFileType(extension)
    FC->>ST: uploadFileToStorage
    alt S3 configured
        ST->>OBJ: PutObject
    else no credentials
        ST->>OBJ: write backend/uploads/key
    end
    ST-->>FC: key + url + bucket
    alt Mongo connected
        FC->>DB: File.create + populate owner
    else memory
        FC->>DB: createFile with embedded owner
    end
    FC-->>AX: 201 file JSON
    FU->>FU: refreshTrigger + 1

In plain words

Upload has two separate jobs: move the bytes, then write the index card.

  1. The dropzone rejects anything over 50 MB.
  2. Axios posts FormData with the token and reports progress.
  3. multer keeps the whole file in RAM, not on disk.
  4. The controller reads the extension to pick a category and builds a key from timestamp + random bytes + extension — never the user's filename, which prevents collisions and path traversal.
  5. The bytes are written to S3, or to backend/uploads when AWS keys are absent.
  6. Only then is the metadata row written (Mongoose, or the in-memory array).
  7. The UI shows a toast and bumps refreshTrigger, so the list re-fetches.

Cost: the file passes through the API, so a 50 MB upload occupies about 50 MB of server RAM while it is forwarded. There is no direct browser-to-S3 upload.

11. List files

Access rule: owner id OR email in users. Each file gets a fresh presigned URL.

sequenceDiagram
    autonumber
    participant P as Dashboard / FilesView
    participant MW as authMiddleware
    participant FC as file.controller
    participant DB as File model or memory
    participant ST as s3.service
    P->>MW: GET /files?types&searchText&sort&limit
    MW->>MW: resolve req.user
    MW->>FC: getFiles
    FC->>DB: find owner = userId OR users has email
    Note right of FC: + type $in / name regex
+ sort / limit
    DB-->>FC: documents, owner populated
    loop each document
        FC->>ST: presign inline (1 hour)
    end
    FC-->>P: total + documents

In plain words

Every page load asks one question: which files may this user see?

  1. The page calls GET /api/files with category, search text, sort and limit.
  2. The guard resolves the user from the token.
  3. The controller keeps files where owner is this user or the share list users contains their email.
  4. It then applies the category filter, a case-insensitive name search, sorting and the limit.
  5. Each file gets its url refreshed: a new one-hour signed link in S3 mode, the stable /uploads/<key> path locally.
  6. The page receives { total, documents } and renders one card per document.

Listing, usage and search all reuse that same filter, which is why sharing behaves consistently. The cost is one signing call per file, every time.

12. Download / open

sequenceDiagram
    autonumber
    participant W as New tab
    participant MW as authMiddleware
    participant FC as file.controller
    participant ST as s3.service
    participant OBJ as S3 or disk
    W->>MW: GET /files/:id/download?token=JWT&inline=true
    MW->>FC: downloadFile
    FC->>FC: find by id
    alt S3 active
        FC->>ST: presign GET
        FC-->>W: 302 presigned URL
        W->>OBJ: fetch bytes directly
    else local disk
        FC-->>W: sendFile or res.download
    else plain url
        FC-->>W: 302 to file.url
    end

In plain words

Opening and downloading are the same endpoint with a different flag.

  1. The card opens /api/files/:id/download?token=JWT&inline=true in a new tab; Download uses the same URL without inline.
  2. The token sits in the query string because window.open cannot send headers.
  3. The controller loads the metadata row — it needs the key, not the bytes.
  4. S3 mode: sign a one-hour GetObject URL, set Content-Disposition, reply 302; the browser downloads from S3 directly.
  5. Local mode: Express sends the file with sendFile or download.

The signed link is a temporary key to the warehouse: valid one hour, and not tied to the user after it is issued, so anyone holding it can fetch the file.

13. File lifecycle

stateDiagram-v2
    [*] --> Uploaded: POST /files/upload
    Uploaded --> Listed: GET /files
    Listed --> Shared: PATCH share
    Shared --> Listed: share list replaced
    Listed --> Renamed: PATCH rename
    Renamed --> Listed: re-fetch
    Listed --> Deleted: DELETE
    Deleted --> [*]
    Uploaded --> OrphanBlob: metadata write failed
    Deleted --> OrphanBlob: blob delete failed
    OrphanBlob --> [*]: manual cleanup

In plain words

A file's life is short and has no undo.

  1. Uploaded — bytes written, metadata saved.
  2. Listed — appears in a list, with a fresh signed URL each time.
  3. Shared / renamed — only the share list or display name changes; bytes and key stay.
  4. Deleted — blob removed, then metadata removed.
  5. Orphan — a failure between the two stores leaves bytes without a record, or a record whose blob is gone. Nothing cleans this up.

There is no trash, no versions and no restore, so delete means gone. Only a backup outside this app can bring a file back.

14. Metadata vs bytes

Two data planes: blobs live in S3/disk, records live in Mongo. Only records are transactional.

flowchart TB
    subgraph CLIENT["Browser"]
        C1["File from input/drop"]
        C2["FormData multipart"]
        C3["React state FileDoc[]"]
        C4["New tab download URL"]
    end
    subgraph SERVER["Express API"]
        S1["multer memoryStorage
whole file in RAM"]
        S2["file.controller"]
        S3["s3.service
timestamp + random key"]
        S4["MongoDB File document"]
        S5["presign GetObject (1 h)"]
    end
    subgraph BLOBS["Blob storage"]
        B1[("S3 object")]
        B2[("backend/uploads/key")]
    end
    C1 --> C2 --> S1 --> S2 --> S3
    S3 -->|bytes| B1
    S3 -->|bytes| B2
    S2 -->|metadata| S4
    S4 -->|JSON + fresh URL| C3
    C4 --> S4
    S4 --> S5 -->|302| C4
    C4 -->|bytes| B1
    C4 -->|bytes via Express| B2

In plain words

Think of a parcel and its paperwork: the bytes are the parcel, the database row is the paperwork, and they travel on separate lanes.

Upload lane. Browser → API → storage (S3 or disk) → key comes back → paperwork written with that key. The key is the only bridge between the two lanes.

Read lane. Listing reads only paperwork. When bytes are needed, the API signs a temporary link and redirects; the browser collects the parcel from storage. Local mode hands it over itself.

Because there are two lanes there is no single transaction across them: a failed metadata write leaves an orphan parcel, and a failed blob delete leaves a stranded one. It also explains the repeated signing — the row stores a key, not a permanent public link.

15. Data model

Owner is a real reference; sharing is an array of email strings.

erDiagram
    USER ||--o{ FILE : owns
    USER {
        ObjectId _id PK
        string email UK
        string fullName
        string avatar
        string password
        string otpCode
        date otpExpiresAt
        date createdAt
        date updatedAt
    }
    FILE {
        ObjectId _id PK
        string name
        string url
        string type
        string extension
        number size
        ObjectId owner FK
        string users
        string s3Key
        string bucketFileId
        string bucket
        date createdAt
        date updatedAt
    }

In plain words

There are only two tables, and one link between them.

  • USER — one row per account: unique email, name, avatar, bcrypt hash, current OTP and expiry. Password and OTP are stripped before anything reaches the browser.
  • FILE — one row per file: name, type, extension, size, owner, share list, and where the bytes live (s3Key, bucket).
  • The arrow means one user owns many files: FILE.owner stores the user id, which Mongo can populate into the full user object.
  • users is not a table link — just an array of email strings. That array is the entire sharing model.

USER is the membership desk, FILE is the item register. The register never contains the file, only directions to it.

16. Who can see what

flowchart TD
    R["Authenticated request"] --> Q["access filter"]
    Q --> O["owner == user._id"]
    Q --> S["user.email in file.users"]
    O --> V["visible in list, usage, search"]
    S --> V
    V --> D{"operation"}
    D --> L["list / usage / search / download
correctly scoped"]
    D --> M["rename / share / delete
no ownership check"]

In plain words

Visibility is one rule, applied in one place.

  • A file is visible if the requester owns it, or their email is in the share list.
  • Listing, usage and search all use that rule, so all three agree.
  • Sharing adds an email; removing it takes access away on the next request. No invitation, no notification.
  • The owner is not automatically in the share list, which is why the rule is an OR.

The right branch is the problem: rename, share and delete never run this rule — a valid token is enough. Visibility is enforced, modification is not.

17. Fallback modes

Every integration fails silently to a working local substitute.

flowchart TD
    BOOT["node server.js"] --> DBQ{"MONGODB_URI set?"}
    DBQ -- no --> MEM["in-memory store
demo user + 5 seed files"]
    DBQ -- yes --> TRY["mongoose.connect, 2 s timeout"]
    TRY -- ok --> MONGO["readyState = 1"]
    TRY -- fail --> MEM
    BOOT --> S3Q{"AWS key + secret + bucket?"}
    S3Q -- no --> DISK["backend/uploads"]
    S3Q -- yes --> S3["S3Client"]
    BOOT --> SMQ{"SMTP user + pass?"}
    SMQ -- no --> CONSOLE["OTP printed to logs"]
    SMQ -- yes --> SMTP["nodemailer sends mail"]

In plain words

At boot the app checks three sockets, like a power strip with backup batteries.

  • Database. No MONGODB_URI → in-memory store with a demo user and five seed files. URI present → connect with a 2-second timeout; failure → memory anyway.
  • Storage. AWS key, secret and bucket all present → S3. Anything missing → local backend/uploads, served at /uploads.
  • Mail. SMTP credentials present → real email. Missing → code printed in the server log.

Every branch is caught, so a misconfigured server still starts and looks healthy. The tells are subtle: data disappears on restart, files vanish when the machine is rebuilt, and no email ever arrives.

In plain words

Read the diagram as four floors of one building.

  • Floor 0 — print shop. Vite reads the TypeScript and React source and writes plain HTML, JS and CSS into dist/. Nothing at runtime needs Vite.
  • Floor 1 — shop counter. React Router picks the page, Tailwind styles it, sonner shows toasts, dropzone handles uploads. AuthContext remembers who is logged in (mirrored in localStorage), and Axios attaches the token to every call.
  • Floor 2 — back office. Express receives HTTP: cors, body parsers, then the router. authMiddleware verifies the JWT and loads the user before any controller runs. Controllers call bcrypt, jsonwebtoken, nodemailer, the AWS SDK or Mongoose.
  • Floor 3 — storerooms. Mongo keeps rows about files, S3 or the disk keeps the bytes, SMTP only sends mail. Dashed arrows are the local stand-ins used when configuration is missing.

One sentence: React asks, Express decides, Mongo remembers what, S3 remembers the bytes, and S3 hands those bytes to the browser directly through a temporary link.

19. Upload and download journey

Two user actions traced through every technology. Upload moves bytes first (browser → multer RAM → S3/disk) and writes the database row second. Download reads only the row, then either redirects the browser to a signed S3 link or streams the file from disk.

In plain words

Upload is a two-store operation, and the order matters. The browser checks size, Axios sends the multipart request with the token, Express parses it, the guard identifies the user, and multer buffers the whole file in RAM. The controller picks a category from the extension and builds a safe key. The bytes go to S3 or disk first; only then is the database row written. The response triggers a toast and a list refresh.

Open/download is shorter because it never needs the bytes in Node when S3 is active. The card opens a URL with the token in the query string (a new tab cannot send headers), the guard verifies it, and the controller loads the row to find the key. S3 mode answers with a redirect to a one-hour signed URL and the browser downloads directly; local mode streams the file through Express.

That asymmetry is why the app feels fast with S3 and slower with local disk.
